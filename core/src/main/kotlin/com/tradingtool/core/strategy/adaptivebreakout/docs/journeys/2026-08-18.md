# Breakout Buy Review console

## Why

The scanner identifies structure, but the user needed a repeatable way to inspect the quality of any historical breakout candle without manually calculating close position, volume, delivery, or ATR distance. The review also needed to work for ceiling days and post-breakout days without mislabeling them as entry signals.

## Implemented

- Added a causal historical endpoint: `GET /api/strategy/adaptive-breakout/buy-review?symbol=...&date=YYYY-MM-DD`.
- Replays adaptive-breakout structure only through the selected date.
- Evaluates five transparent checks: close position, prior-10D volume, prior-20D delivered quantity, close clearance above the breakout line, and ATR extension.
- Returns `PASS`, `WAIT`, or `REJECT` only for a fresh-breakout session; other structure days return `CONTEXT_ONLY`.
- Treats missing inputs as `UNAVAILABLE`; a fresh breakout with missing evidence returns `WAIT`.
- Uses the pre-breakout ceiling boundary even when the breakout candle also starts a newer structural turn.
- Added a dedicated compact console and a dated deep link from each Adaptive Breakout scanner row.

## Decisions and trade-offs

- Kept the review separate from the scanner to preserve scanner density and make historical date changes easy.
- Baselines exclude the selected session to avoid contaminating the comparison.
- Used delivered quantity rather than delivery percentage for participation confirmation.
- SMA 50/200 are context values, not part of the five-rule verdict.
- Excluded next-day gap, stop, order type, and fundamentals from this first screen.

## Validation

- Adaptive engine and breakout-quality unit tests cover causal breakout boundaries, complete confirmation, missing delivery, and context-only sessions.
- Frontend tests cover the rule-first layout, API query, selected-day evidence, overall verdict, and scanner deep link.
- Resources module compilation and frontend production build pass.

## Chart context and next-morning execution

Extended the same console so a fresh-breakout signal is not mistaken for an automatic buy. The API now returns causal 50/200 SMA context, five- and twenty-session SMA direction, the prior 52-week high, the nearest overhead obstacle, and remaining room in percent and ATR. The 200 SMA is a context gate: flat or rising is acceptable, while price below a falling 200 SMA rejects the setup. Less than 1 ATR to resistance rejects; 1–2 ATR waits; at least 2 ATR passes.

The page now accepts a next-session opening price. It applies the documented entry zones from the breakout line: up to 0.25 ATR is a consideration zone, 0.25–0.50 ATR waits for a pullback/limit, above 0.50 ATR is not chased, and below the line is rejected. Breakout-day and chart-context failures remain binding. A reusable one-line buy/sell/% calculator sits underneath.

Validation: focused Kotlin analyzer tests, execution-rule unit tests, page rendering tests, core compilation, and the frontend production build pass.

## Six-month breakout test

The user also asked for a deliberately small price-only validation: select one stock, replay the latest six calendar months of the adaptive-breakout engine, enter at the next session open after each completed fresh breakout, and apply a fixed +5% target / -5% stop. Added `POST /api/strategy/adaptive-breakout/backtest/run` and a `Breakout 6M Test` page with a stock search, summary counts, holding days, and trade-by-trade replay. The test window is clipped to the data actually available, so a short candle history is not presented as a full six months.

The evaluator uses one position at a time. When a daily candle touches both target and stop, it conservatively assumes the stop happened first and labels the ambiguity. An unclosed position exits at the last available close as `END_OF_TEST`.

Validation: `AdaptiveBreakoutBacktestEngineTest` covers target, stop-first ambiguity, and end-of-test exits; `AdaptiveBreakoutBacktestPage.test.tsx` covers selection and request values; core tests, service packaging, and frontend production build pass.

## Delivery evidence display fix

The scanner's 20D modal was mapping delivery to `null` even though `/api/stocks/by-symbol/{symbol}/detail` already returned `delivery_days`. The modal now joins those records by date. Breakout Buy Review now shows both delivery percentage and delivered quantity, using the stock-detail payload as a fallback when needed. BHEL's 17 Aug response was verified against the running API: 39.39% delivery and 6,046,709 delivered shares.

Validation: scanner and historical-review frontend tests pass, including a delivery row assertion, and the frontend production build passes.

## Early breakout watch state

Added `EARLY_BREAKOUT` as a lower-confidence observation without changing the confirmed-ceiling or `FRESH_BREAKOUT` paths. When a completed close first clears a live compact candidate's peak plus 0.10 candidate-day ATR, replay records an early event before the day's higher high can reset that candidate. It does not mutate the active ceiling, populate official breakout evidence, increment fresh-breakout counts, enter the six-month backtest, or qualify as a Buy Review entry day.

The scanner gives this state its own blue filter and row treatment. The structure cell shows the provisional early line, labels the state `Watch only`, and continues to show the older confirmed ceiling when one exists. Raw replay records the causal candidate, early boundary, and plain-language explanation. NETWEB's ₹4,744 candidate / ₹4,770.21 early line and HFCL's 3 Aug move are regression cases.

Validation: focused engine and Buy Review tests pass (15 tests), the scanner page test passes (8 tests), the full service package compiles, and the frontend production build succeeds. Existing large-bundle, shaded-JAR overlap, and Kotlin annotation warnings are unchanged.

## Single-stock scanner mode

The Adaptive Breakout console can now run the existing scanner for one selected NSE equity as well as a watchlist. The control bar has an explicit Watchlist/Stock switch and reuses the standard instrument search. The scan endpoint accepts exactly one input: `watchlist` or `symbol`. For a symbol request, the backend resolves the NSE instrument token and sends it through the same five-year candle load, engine configuration, row mapping, raw replay, LTP overlay, and evidence UI used by watchlist rows.

This is intentionally one analysis path rather than a separate single-stock algorithm. Unknown symbols, insufficient candle history, missing input, and conflicting inputs return a clear bad request.

Validation: the Adaptive Breakout page suite passes all 9 tests, including stock selection and the `scan?symbol=ABC` request; the frontend production build and full service package succeed. Existing bundle-size, shaded-JAR overlap, and Kotlin annotation warnings are unchanged.
