# SMA200 Limit-Entry Backtest

## Feature and why it was built

Added a simple single-stock backtest to test the existing SMA Buy Zone idea: place a limit order at exact SMA200 whenever the day low reaches SMA200, then measure forward performance.

## What was implemented

- Added NSE stock selection through the existing instrument search.
- Added a one-calendar-year test window with 800 days of warmup data for SMA200.
- Counted every SMA200 low touch, entered only the first eligible touch, and blocked new entries until the 40th future trading session had closed.
- Added entry-date context matching the SMA screener and close-to-close returns after 10, 20, and 40 trading sessions.
- Added the `SMA200 Backtest` navigation page and `/api/strategy/sma200-backtest/run` endpoint.

## Key decisions and tradeoffs

- A touch means `daily low <= SMA200`; the assumed fill is exactly SMA200.
- Returns use the close on the specified future trading session. Recent trades remain visible with missing values for horizons not yet available.
- The backtest is intentionally price/SMA-only; volume and Wyckoff context remain separate validation steps.

## Dropdown reliability correction

The initial empty dropdown was not caused by selected-stock filtering. The live `/api/stocks/instruments` endpoint returned zero rows because the Kite access token had expired and the in-memory instrument cache could not populate at startup. The endpoint now reloads an empty cache on demand after authentication and explicitly reports when Kite login is required. The shared search component uses the neutral `No stocks found` state unless a caller has actually supplied existing stock tokens to exclude.

## Golden Buy Zone filter

Added two compact quick-filter controls to the SMA Buy Zone Screener: `All stocks` and `Golden Buy Zone`. Golden Buy Zone uses the existing scanner field `sma200TouchedInLast5d`, so it returns only stocks whose low touched SMA200 during the last five trading sessions. The SMA200 touch flag is also visible in the table, keeping the selection rule auditable without changing the scanner API or Wyckoff logic.

Validation: `npm --prefix frontend run test:run -- src/pages/HotSmaPage.test.tsx` passed (3 tests), and `npm --prefix frontend run build` passed.

## Selectable entry SMA

The SMA limit-entry backtest now defaults to SMA200 but accepts SMA100 and SMA50 from a compact selector. The selected value is validated by the backend, returned with every report, and used consistently for low-touch detection, exact limit fills, touch counts, and all forward-return calculations.

Validation: focused Kotlin service tests, resource compilation tests, SMA backtest page tests (including SMA50 selection), and the frontend production build passed.

Live local validation: an INFY request with `entrySmaPeriod: 50` returned `entrySmaPeriod: 50`, 174 touches, and 5 non-overlapping trades.

## Kite candle cache-aside

Removed Supabase from daily and intraday candle reads so every workflow now uses one simple path: Redis first, then Kite on a cache miss. Exact requested ranges are cached for three hours through `CANDLE_CACHE_TTL_SECONDS`; Redis failures degrade to Kite without interrupting calculations.

The candle tables, DAOs, persistence handler, scheduled refresh job, and workflow-level synchronization logic were removed. Supabase remains unchanged for non-candle data. Validation covered daily and intraday cache hits/misses, the 10,800-second TTL, 194 core tests, two service tests, and compilation of the complete Maven reactor.
