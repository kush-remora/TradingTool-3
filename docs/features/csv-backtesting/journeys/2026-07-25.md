# CSV Backtesting: Sector Table Filter Fix

The Trade Details sector filter did not reliably update the visible rows because the page duplicated Ant Design's filter state in both a custom dropdown and an external data filter.

The table now uses Ant Design's native tree-mode filter and row predicate as the single source of truth. Tree mode provides a real Select All checkbox that checks every sector while preserving filter search. The Maximum V2 Run filter excludes rows without a V2 metric whenever a limit is active, as well as rows above the limit. V2 now finds its run base using the lowest low in the previous 50 trading sessions, then averages the six closes ending on that low. Validation: focused V2 validator tests and the production frontend build completed successfully.

The Trade Details table now includes **Breakout Day Move %**. It is calculated from the signal-day candle only: `(close - open) / open * 100`, so it remains independent of the selected entry strategy. The value is returned for both entered and unfilled signals, when the signal candle is available.

## Duplicate-row and combined-filter correction

A live duplicate fixture exposed the deeper failure: duplicate symbol/date signals generated duplicate response rows, while the table also used symbol/date as its React key. Changing Maximum V2 Run then caused React to retain excluded rows and duplicate other rows.

- Deduplicate backend signals by symbol and signal date before validation, trade generation, and summaries.
- Defensively deduplicate frontend rows and give each row a stable identity.
- Memoize the table data and sector options so a V2 maximum does not churn filter inputs.
- Synchronize the displayed count with both Maximum V2 Run and selected sectors.

## Filtered SL outcome line

Added a compact result line that recomputes from the rows matching both Maximum V2 Run % and the sector table filter. It reports filtered total, SL Yes, SL No, and success rate, where success rate is the percentage of filtered rows whose SL value is No. This keeps the metric aligned with exactly what the user sees in Trade Details.

Validation: 6 focused frontend tests passed, including mixed and empty SL outcomes, and the production frontend build passed.

## Forty-day maximum holding period

An entered trade now has a maximum holding period of 40 calendar days. If the configured target or stop loss has not already exited the trade, the engine closes it at the close of the first trading candle on or after entry date plus 40 days. The ordinary stop and target checks retain priority on that day. This applies to both fixed-target and trailing-stop backtests.

Validation: focused fixed and trailing exit evaluator tests passed.

## Breakout delivery context

Trade Details now displays two delivery-only context columns from the persisted NSE delivery history: **Breakout Delivery %** for the signal date, and **T−5 Max Delivery %** for the five completed trading sessions before it. Missing source rows remain blank. These measures do not change trade selection, entry, or exit behavior.

Validation: focused delivery-metric test, CSV table tests, Kotlin service compilation, and production frontend build passed.

## Configurable V2 breakout lookback

The V2 breakout validator no longer forces every experiment to use a 100-session prior-high baseline. The CSV Backtesting Engine now exposes **Breakout lookback (trading sessions)**, accepts 20-250 sessions, and retains 100 as the default.

The selected value controls both the breakout resistance baseline and the preceding fresh-breakout suppression window. The service also expands its historical candle range for longer windows so validation has enough prior sessions. This remains a per-run request setting; no persistence or new configuration service was added.

### Fresh-breakout window correction

The configured window follows Chartink's completed-session offset: a 60-session breakout compares today's high with the maximum close of the 60 completed prior sessions. Freshness requires that none of the preceding 59 sessions satisfied that same rule. Regression coverage verifies repeated-breakout suppression.

### Mandatory fresh-breakout validation

Live reproduction with AADHARHFC confirmed the repeated rows were produced when the V2 switch was off: the service skipped all breakout validation and accepted every CSV date. Fresh-breakout validation now always runs using the configured 10-250 session window. The renamed **Apply additional V2 filters** switch controls only volume-spike, extension, and recent-base rules. Next-day-open results now display the validated breakout level instead of a blank value.

Validation: the exact five-date AADHARHFC reproduction with a 10-session window accepts only 08-Apr-2026 at the ₹471.30 maximum-close breakout level. The four later dates shown in the reported table are rejected with additional V2 filters disabled.

### Close-based breakout resistance

Aligned the validator with the Chartink rule `Daily High > 1 day ago Max(N, Daily Close)`. The breakout level is now the maximum close across the configured number of completed prior sessions, not the maximum prior high. Freshness still checks the preceding `N−1` sessions using the same high-versus-prior-closes expression.

Live ATUL validation: both 21-Apr-2026 and 22-Apr-2026 are raw 60-session close-based breakouts above ₹6,674. Neither is fresh because earlier raw breakouts remain inside the 59-session suppression window; the 10-Apr through 22-Apr batch returns zero validated signals.

## Maximum breakout span

Trade Details now shows **Breakout Span** for each accepted signal. The configured breakout lookback still decides whether the signal is eligible; this new value is diagnostic only. It counts backward from the signal date until the most recent completed session whose close was greater than or equal to the signal-day high.

The scan is capped at 500 trading sessions. An exact result is displayed as `120 days`; when no blocking close exists inside available or capped history, it is displayed as a lower bound such as `500+ days`. The service loads 800 calendar days by default so established stocks normally have enough data for the full scan.

## Initial stop before trailing stop

**Target + Trailing SL** now has two stop phases. The target remains active throughout. During the configurable initial trading sessions, including the entry session, the engine uses the entry-price-based initial stop only. Once that many sessions have completed, it activates the configured trailing stop from completed candle closes. For example, 10% initial stop + 3 initial sessions + 5% trailing stop uses 10% protection on sessions 1-3 and can first apply the 5% trail on session 4.

The UI exposes **Initial Stop Loss %**, **Initial Stop Sessions**, and **Trailing Stop %** only for trailing mode, with defaults of 10%, 5 sessions, and 5%. Fixed Target & SL behavior is unchanged. Existing API clients retain the same initial-stop field and receive defaults for the two new values.
