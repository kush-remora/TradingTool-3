# Gemini configuration wiring

## Why

The visual book generator will call Gemini from the backend, so its API key must remain outside browser code and tracked files.

## Implemented

- Added a typed Gemini setting to the backend configuration.
- Added the ignored local `localconfig.yaml` with an empty Gemini key placeholder.
- Declared `GEMINI_API_KEY` as a Render secret.
- Added a configuration test for local-key and environment-key precedence.

## Decision

Render's `GEMINI_API_KEY` takes precedence; local development can use the ignored `localconfig.yaml`. The actual key is deliberately not copied from any tracked document.

## Folio persistence schema

### Why

A source PDF and its page-level conversion progress must survive a browser refresh so a large book can resume safely.

### Implemented

- Added `public.folios` for book context, private Storage location, source-file metadata, overall status, and error state.
- Added `public.folio_pages` for extracted page content, image references, generated layout choices, selected option, page status, and errors.
- Added the migration and kept the canonical base schema in sync.

### Decisions and trade-offs

- PDF bytes stay in the already-created private `ey-books` Storage bucket. The database stores its bucket and object path only.
- A unique `(folio_id, page_number)` and a `(folio_id, status, page_number)` index make resume and next-page queries deterministic.
- Upload, extraction, and Storage API credentials are intentionally separate follow-up tasks.

## Folio upload and status list

### Why

The MVP needs a durable entry point: upload a source PDF once, then return to the same folio rather than re-entering book context for every page.

### Implemented

- Replaced the first-page form with `New folio` and `Your folios` tabs on `/book-generator`.
- Added `POST /api/folios` for a title, objective, optional theme, and one PDF; it validates the PDF signature, extension, file name, and 50 MB limit.
- Added private Supabase Storage upload to `ey-books/folios/<uuid>/source.pdf`, followed by a parameterized `folios` insert with status `uploaded`.
- Added `GET /api/folios`, returning a bounded recent list used after refresh and immediately after creation.
- If database insertion fails after storage upload, the backend makes a best-effort removal of the new object.
- Added Render declarations for `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; only ignored local config holds local values.

### Decisions and trade-offs

- Upload precedes the database insert, so an unavailable bucket cannot leave a false `uploaded` row. The compensating delete handles the inverse failure case.
- The source bucket stays private; browser code never sees the service-role key.
- PDF parsing, page conversion, per-page resume controls, and downloads are intentionally deferred.

## Enterprise Structured Documentation & Zero-Crop Visual Re-Composition

### Why

The MVP visual book generator was collapsing structured technical documents (such as resumes, system architecture specs, and workflow manuals) into an unformatted wall of text because PDFBox single newlines were collapsed by `split("\n\n")` and standard CSS. Furthermore, technical diagrams and workflow figures were severely chopped off by `object-fit: cover`. In an enterprise software company (like EY), product authors create meticulously formatted documents and UI designers provide architectural workflow diagrams. The tool must faithfully preserve document hierarchy and ensure diagrams are never cropped.

### Implemented

- **Structured Document Parser & Formatter (`StructuredDocumentRenderer.tsx` + `structuredDocument.css`)**:
  - Implemented typed parsing into `doc-title`, `doc-subtitle`, `doc-contact`, `section-header` (with divider lines), `sub-header` (role/dates with accent left borders), `key-value` specs (bold keys), `bullet-list` (`•` items with bold lead-ins), and paragraphs.
  - Added smart line continuation merging so wrapped lines from PDFBox extraction stay attached to their parent bullet or paragraph without breaking hierarchy.
- **Zero-Crop Technical Diagram Containers (`bookGenerator.css`)**:
  - Replaced destructive `object-fit: cover` and fixed heights with `object-fit: contain !important; max-height: 480px; width: 100%;`.
  - Added dedicated `.book-page-figure-caption` rendering beneath diagrams.
  - Rebalanced side-by-side grid to `minmax(0, 1.3fr) minmax(320px, 0.9fr)`.
- **Structured PDF Export (`VisualBookPdfDocument.tsx`)**:
  - Replaced raw text dumping in `@react-pdf/renderer` with `renderPdfStructuredBlocks()`, outputting formatted section dividers, bold subheaders, key-value rows, indented bullet items, and uncropped images with `objectFit: "contain"`.
- **Backend Art Director Prompt & Schema (`VisualBookLayoutService.kt`)**:
  - Aligned Gemini prompt with Enterprise Technical Documentation Art Director persona.
  - Added typed `figureCaption` property across prompt, JSON schema, and fallback responses.

### Decisions and Trade-offs

- Document parsing runs deterministically on the extracted text client-side, ensuring instant rendering and zero latency without requiring an extra LLM round-trip just to format bullets.
- Diagram framing uses `object-fit: contain` with subtle backdrop framing (`#fbfaf6` and light borders) to guarantee 100% of the diagram content is visible regardless of aspect ratio.

- IntelliJ Maven tests: `VisualBookLayoutServiceTest` (2 tests, 0 failures) and `FolioServiceTest` (4 tests, 0 failures) passed.

## Page reader and on-demand text extraction

### Why

The MVP needs a resilient page-by-page reader checkpoint before layout generation. Users need to browse the verbatim text of any page in an uploaded Folio, with zero re-extraction overhead across page refreshes.

### Implemented

- Added Apache PDFBox 3.0.8 dependency and `HttpRequestExecutor.executeBytes` for binary streaming.
- Added `downloadPdf` to `FolioStorage` & `SupabaseFolioStorage`.
- Added `getPage(folioId, pageNumber)` to `FolioService`:
  - Returns cached page text from `public.folio_pages` immediately if present.
  - On cache miss, streams private source PDF bytes, uses PDFBox `Loader.loadPDF` and `PDFTextStripper` to extract single-page text, updates `folios.page_count`, and persists the extracted text with status `ready`.
- Added `GET /api/folios/{id}/pages/{pageNumber}` endpoint in `FolioResource`.
- Added comprehensive unit tests in `FolioServiceTest.kt` verifying PDFBox extraction, `page_count` synchronization, and cached retrieval without storage calls.
- Updated `frontend/src/bookGenerator/BookGeneratorPage.tsx` and `bookGenerator.css`:
  - Interactive Folio cards in "Your folios" with "Read pages →" action.
  - Dedicated Reader view displaying Folio title, objective, page counter (`Page X of Y`), Back/Next page navigation, verbatim text sheet, and graceful loading/error/empty states.
  - URL query parameter synchronization (`?folioId=...&page=...`) so page reloads immediately restore the active page from database checkpoints.

### Decisions and trade-offs

- Text extraction happens on-demand per page and is cached in `folio_pages`, avoiding long background queues or full-document pre-processing for large PDFs.
- Verbatim text is preserved without modification or rewriting, adhering to the re-composer principle in `concepts_brief.md`.

- Vitest test suite executed: 230 tests passed with 11 pre-existing unrelated failures (no regressions).

## Restructuring Exercise: Decoupling Assignment into Standalone EVI Module

### Why

The repository is primarily a personal trading system. To prepare for sharing or submitting the EY assignment code without exposing proprietary trading algorithms, Wyckoff screeners, or Bhavcopy infrastructure, all assignment code needed to be isolated into a self-contained `evi/` module.

### Implemented

1. **Top-Level `evi/` Module Architecture**:
   - Established `evi/backend/` as an independent Kotlin Maven module under clean package namespace `com.evi.*` with zero dependencies on `com.tradingtool.*`.
   - Created `EviHttpClient` and `JdkEviHttpClient` wrapping JDK 21 HTTP client, eliminating coupling to core trading HTTP models.
   - Created `EviJdbiHandler` and `FolioDao` for standalone PostgreSQL persistence.
   - Migrated `VisualBookLayoutService`, `FolioService`, `VisualBookResource`, and `FolioResource` with all unit and validation tests into `evi/backend`.
   - Removed all visual book classes from `core/` and `resources/` (including deleting `pdfbox` from `core/pom.xml`).
2. **Backend Lifecycle & Deployment Integration**:
   - Added `<module>evi/backend</module>` to root `pom.xml` and `COPY evi evi` to `Dockerfile`.
   - Connected `evi-backend` dependency into `service/pom.xml` and registered resources into Dropwizard's Jersey pipeline in `Application.kt` and `ServiceModule.kt`.
3. **Frontend Isolation**:
   - Created `evi/frontend/` as a standalone React 19 + TypeScript + Vite project with its own `package.json`, `tsconfig.json`, `index.html`, and `vite.config.ts`.
   - Moved all book generator UI components and CSS to `evi/frontend/src/bookGenerator/`.
   - Updated root `frontend/src/main.tsx` to mount the `evi/frontend` component cleanly so the live development server and Render deployment work without interruption.
4. **Authority Mode Prompts & Artifacts**:
   - Packaged the canonical prompt suite (`1-preserve.md`, `2-restructure.md`, `3-transform.md`, `README.md`) under `evi/prompts/`.
   - Placed the schema migration under `evi/db/schema.sql`.
   - Authored an executive `evi/README.md` explaining the problem framing, the three authority modes, architecture, and standalone run instructions.

### Decisions and Trade-offs

- Selected Option A (self-contained top-level `evi/` directory) so the entire assignment can be shared, zipped, or extracted into a standalone Git repo at any time.
- Decoupled `evi/backend` packages from `com.tradingtool.*` so the exported codebase looks 100% purpose-built for the assignment.
